# Songs store absolute Note Numbers; pitch settings are rewriting Basepoints

The v4/v3 formats stored the nominal id and kept pitch outside the note — a play-time playback-rate label — which left every surface translating between id spaces and made an all-notes piano-roll view impossible to state. We decided (2026-08-19) that every note in every format stores an **absolute MIDI Note Number on one shared axis, Basepoint included**: for **pitched buttons** the sounding pitch the listener hears (derived per button from `baseNote` at registry build — nearest chromatic match to the nominal, validated); for **assigned buttons** (`pitched: false` in config — percussion, SFX, and chord strums like Ukulele's G7 button) the button's Nominal Id carried by the Basepoint. Pitch settings (song-level plus per-track override) become **Basepoints**: changing one rewrites the affected tracks' numbers by the interval, stranded notes included. Switching a track's instrument rewrites button-preservingly through nominal correspondence (Lyre→Vintage-Lyre still re-flavors; cross-layout swaps strand as before), and cross-game conversion stays sound-preserving (carry, octave-fold, strand). Formats bump to composed v5 / recorded v4 / vsrg v3 with lazy upgrade on load; the compressed composer view keeps the Song Grid as its view function (off-scale notes render nearest-row with an accidental hint), while a future pure view renders the axis by linear scaling — the architecture is one absolute axis plus a view function per surface. Supersedes ADR-0001's song-side identity; Nominal Ids survive as the instrument/grid namespace, so ADR-0004/0005 hold under the new vocabulary.

## Considered Options

- **Nominal + folded Basepoint only** ("transposition-absolute") — rejected: bakes a known lie into the new format for tuned instruments (the roll shows D where the button's own label and the ear say Db), and upgrading to honesty later means migrating every song a second time.
- **No format change** (a future pure view derives the axis at render time) — rejected: pitch stays load-bearing at runtime forever, and "changing pitch moves notes" becomes a UI illusion instead of a format truth.
- **Sound-preserving instrument swap as the default** (pure DAW) — rejected: Lyre→Vintage-Lyre would strand D/E/A/B instead of re-flavoring them, killing behavior users rely on. May appear later as an explicit secondary choice.
- **Chord/SFX marking via a baseNote convention** — rejected: an identity class hidden inside a display string; a stray character silently flips a button's class instead of erroring. Explicit `pitched: false`; `baseNote` becomes a free display label ("G7").
- **Authoring explicit soundingMidi** — rejected: restates `baseNote` and can drift from it. Derivation plus build-time validation instead (a non-pitch-class `baseNote` on a pitched button is an error).
- **MIDI import preserving accidentals + auto-Basepoint detection** — deferred, not rejected: import keeps snapping to white keys for parity today; the format can host accidental-true import later with no further migration. (2026-08-21: the Basepoint half of that deferral was narrower than it read, and is closed. A file's midi numbers are absolute sounding pitches — that is what the honest export writes — so import now takes the layer's Basepoint OFF before snapping onto the grid and carries the snapped nominal back through that layer's own instrument (`nominalToNumber`). Export and import are inverses at any Basepoint; before, our own non-C export re-imported lifted twice, with distinct notes colliding onto one grid row. Still deferred: preserving accidentals, and INFERRING a Basepoint a file neither names in a key signature nor carries in our metadata.)

## Consequences

- `baseNote` is promoted from cosmetic label to load-bearing data: a one-time by-ear audit of the deviant instruments (Vintage-Lyre, Ukulele, LingeringEuphonia, the SFX set) precedes migration — this session already reclassified Ukulele/Euphonia's "second G" as a G7 chord button — and registry validation guards it afterwards.
- Basepoint changes and instrument swaps become real, undoable edits (they rewrite notes), no longer free label flips.
- Stranded Notes generalize: off-scale numbers between grid rows render nearest-row with an accidental hint; strands move with their track on Basepoint changes, pass through swaps, and can un-strand.
- Legacy decode gains one step (frozen tables → nominal → sounding); stranded pre-migration notes migrate best-effort as `id + Basepoint offset`. MIDI export becomes transposition-honest for the first time. `toOldFormat` export is deleted (kept as commented reference); old-format import stays.
- The id→button→id round-trips and the `MIDI_MAP_TO_NOTE`/`NOTE_MAP_TO_MIDI` tables retire.
- Third-party tools that read song JSON without checking `version` will misread v5/v4/v3 numbers as nominal ids.

## Addendum (2026-08-26): the register joins the derivation — meta.json `register`; the authored field `midi` becomes `nominal`

Sky's samples exposed a case the original derivation could not spell: eleven Instruments whose keyboards are the nominal 60–84 grid but whose in-game sound sits whole octaves away (Contrabass plays C1–C3, Horn/Cello C2–C4, Guitar/Harp/Light Guitar/Pipa/Saxophone/Toy Ukulele C3–C5, Winter Piano/Xylophone C5–C7). The nearest-chromatic rule reaches at most ±5 semitones, so their Sounding Pitches were wrong by construction — every stored number, MIDI export and Pro-View row claimed C4 for a button the ear hears at C1.

Decided: the derivation gains an authored, instrument-level **register** — meta.json `register`, an absolute note name ("C1"; C4 = 60) anchoring the LOWEST Pitched Button to the pitch its samples actually sound. The registry takes only the OCTAVE from the anchor: its pitch class must equal the lowest button's own derived class (validated — a register can never transpose by semitones), so every Pitched Button moves by the same whole octaves. This stays inside the "derive, never author `sounding`" rule: `baseNote` still owns the pitch CLASS per button and the register owns only the OCTAVE per instrument, two orthogonal facts that cannot drift into each other. Assigned Buttons are untouched (their Note Number is their Nominal Id), Nominal Ids never move (grid rows, swaps, MIDI-import snapping and legacy decode are unchanged), and the registry also rejects a register on an instrument with no Pitched Button and an anchored pitch outside MIDI 0–127. (Considered and rejected: a relative octave-shift integer — same tables, but it states a delta against a grid octave the author must know rather than the audible fact a pitch detector reports; per-register preset copies — 4 near-identical 15-row tables in lockstep, and inline-notes instruments like the loop-annotated Cello would still need the field; per-note authored soundings — 15 restatements per instrument of one instrument-wide fact.)

With the register making the split explicit, the authored per-note field `midi` was renamed **`nominal`** (presets.json rows, inline meta.json notes, the normalized `InstrumentNote` struct): the field is the button's NAME in the game's grid namespace — the sheet position it occupies, the written pitch of a transposing instrument — and for eleven instruments it now visibly differs from what sounds, so a name that read as a pitch had become actively misleading. Songs never contained it; the rename is config + code + regenerated living fixtures only.

**2026-08-27 — the register translates the WHOLE instrument, Assigned Buttons included.** As first written the register moved Pitched Buttons only, on the reasoning that a button with no single pitch has no pitch to place. Genshin's Ukulele disproved that: its top row is seven Assigned chord buttons holding Note Numbers 72–83 (their Nominal Ids), and the register its pitched rows need (+12, measured and confirmed by ear) walks its middle row onto exactly those seven numbers — the registry rejects the instrument outright. The fix is to make the translation rigid: every button moves by the same displacement, which **cannot** create a collision, because the button set was distinct before it and translation preserves distinctness. Moving only half the instrument is what can, and did. So an Assigned Button's Note Number is its Nominal Id carried by the instrument's register _and_ the Basepoint; the number stays what it always was — an identity, not a pitch — and rigidity is what keeps those identities safe. Exactly one shipped instrument is affected (the Ukulele: chord row 72–83 → 84–95), since it is the only one in either game with both a register and Assigned buttons. Two consequences: genshin's Addressable Span grows from C3–B5 to C3–B6, so its Pro View axis gains twelve rows only chord buttons can occupy; and those chord identities stop sharing numbers with real C5–B5 pitches, which is the more honest arrangement on an axis that means sounding pitch everywhere else.

Because playback resolves numbers through the same sounding tables that migration writes, a legacy file's audio is untouched: the button and playback rate a v3/v2/v1 note resolves to are byte-identical before and after a register change (the parity suite pins exactly this — its sky fixtures were extended with all eleven instruments, recorded by the PRE-register build, and pass unchanged under it). What does change is the current formats' stored numbers for those instruments — accepted deliberately while v5/v4 exist only in beta; at release the incoming population is v3-and-older, which decodes through nominal correspondence and lands on the corrected registers automatically.

## Addendum (2026-10-02): the legacy sheet fields come back BESIDE downloads, never instead of them

Retiring `toOldFormat` cost Sky users something the original decision did not weigh: every Sky download used to be a hybrid, the current file plus the legacy sheet fields (`songNotes`, `pitchLevel`, `isComposed`, `bitsPerPage`, `isEncrypted`), and third-party Sky sheet tools read only those. v5 downloads stopped working in them.

Decided: downloads carry those five fields again, ADDED beside the whole current file, when the running game's config sets `features.legacySheetExport` (Sky: on, Genshin: off - Genshin never had them). One function builds every download (`core/Songs/legacySheetExport.ts`; the player's song and "download all", the composer, the error page), and the fields come from `legacySheetFields()` on ComposedSong/RecordedSong through the restored `numberToNominal`, byte-identical to what the pre-flip exporter wrote for the same songs (pinned against the frozen fixtures' `oldFormatExport` members).

What the original objection was about stays true and stays answered: those fields are a LOSSY VIEW (no Note Number, no duration, only the frozen default-table buttons), so they must never be what the app reads back. They aren't: this app and the pre-v4 one both look at `songNotes` only in a file with no `data`, and every v5 file has one, so a re-imported download takes the lossless path. The rest of the old export - `columns`/`version: 3` for composed, flat `notes`/`version: 2` for recorded - is deliberately NOT restored: with `columns` present the pre-v4 composer would accept a v5 file, decode no notes, and could save that empty song over the user's own; without it the pre-v4 app rejects the file cleanly as invalid. A download whose view had to leave notes out says how many in a non-blocking warning; the file itself always has all of them.

## Addendum (2026-10-04): a song can play on the listener's own instrument and Basepoint, moved by button

Removing the player's "sync song data" setting followed from this decision: a song's numbers only mean what was written at their Basepoint, so sounding them at the listener's Basepoint, or on the listener's instrument, silences whatever that instrument has no key for. Users missed it anyway, because they used songs to hear how other instruments sound.

Decided: the player brings it back inverted, as "don't sync the song's instrument and pitch" (off by default). When it is on, a run plays the song MOVED onto the user's instrument, Instrument Settings, Basepoint and reverb, using the two rewrites the composer already makes. The instrument swap's nominal correspondence keeps each note on the same key of the layout, and the Basepoint change keeps the same buttons. It is the old setting's behavior (which kept buttons, back when songs stored them) spelled in this format, and it is what playing the sheet on another instrument in-game does. A note whose key the user's instrument lacks passes through and strands, as in any swap. Only the run's own clone is rewritten (`core/Songs/songRetarget.ts`): the stored song never changes, tracks keep their volume, Mute and Solo, and the note list keeps its length and order, so the Section still addresses the same notes.

Rejected: sounding the stored numbers on the user's instrument (keeping absolute pitch, swapping only the timbre). Only the part of the melody inside the instrument's range would sound, so a Lyre song on a high-register instrument goes mostly silent, and the user's pitch could never apply.

## Addendum (2026-11-01): a swap carries a key-less note by the register, so swapping back restores the track

A user's Piano song at Gb came back with every Gb4, Cb4 and Db5 an octave up, saved. They had switched the layer to a handpan and back. The swap left a note whose nominal the new instrument has no key for at its old number, claiming it would strand there. On a registered instrument that is false: the handpan's register (D3, a whole octave below its D4-authored nominals) makes its F5 key sound F4, so the "stranded" F4 was voiced by the F5 key. The swap back is button-preserving and took it to Piano's F5. Any F5 already in the column merged with it and was lost. In Sky, 233 of 1892 instrument pairs lost notes on a there-and-back swap, and 3 of 132 in Genshin.

Decided: a stranded note is one of two kinds, and the register applies to exactly one of them (`noteIds.strandedRow`). A **row strand** is a grid row its instrument has no key on: what a swap leaves where the new instrument lacks a note's nominal, what a legacy file's key-less id decodes to, what the move tool lands on an empty row. It is written as that row carried by the instrument's **register shift** (the whole octaves its `register` translates it by; `noteIds.registerShift`, recovered exactly from any button because a `baseNote` flavor is at most ±5 semitones). A rigid translation of a row the instrument lacks can never land on the translation of one it has, so a row strand is stranded on its own row and nowhere else. A **pitch strand** is every other stranded number: a note that keeps its pitch on purpose (a paste between instruments, a Pro View placement, a cross-game import, a MIDI import kept out of range) and falls outside its instrument, or sits on a row whose key sounds something else (Vintage-Lyre's flavors). `nominalToNumber` lifts a missing grid row as a row strand, and `numberToNominal` reads a stranded number back as its row when it is a row strand and as `number − offset` otherwise, the pre-register reading. The swap takes a voiced note by its key's nominal and a row strand by its row, through that pair; a pitch strand passes through unchanged and un-strands where the new instrument sounds its pitch, exactly as every strand did before (ADR-0011 relies on it). Swapping back restores every voiced note and every row strand between any two instruments with no per-button flavor. A scan over every addressable number, instrument pair and Basepoint finds none lost in either game: Sky had 9,216 voiced-note and 4,020 row-strand losses, Genshin 252 and 228. The compressed view's stranded fallback row (`gridRowForNumber`), legacy decode and the legacy sheet export read through the same pair, so a key-less note draws, migrates and exports on the row it belongs to. The move tool's scale steps need no change, because the shift is whole octaves and the scale repeats by octave.

What this changes: on a registered instrument a key-less note now strands on its own row instead of sounding the key an octave away. Legacy files' key-less ids decode that way too, so a note that never sounded keeps not sounding. Without a register on either side every number is exactly what it was. What stays lossy is what always was: a pitch strand that un-strands on the new instrument becomes that key, and the key is what a swap back carries; and a pitch strand that passes onto another instrument can read THERE as a row it lacks (on a narrower one, or one registered differently) and come back moved, onto the row's key or by the registers' difference. Pitch-strand round-trip losses: Sky 135,850 (from 96,828, of 1.6M scanned), Genshin 3,912 (from 3,000). The layer panel's pick session makes any audition within one visit exact regardless. As first committed, this addendum treated EVERY strand as a row. That was more reversible for strands (26,688 Sky cases), but a part pasted onto the wrong layer no longer played once the layer was switched to its instrument, and strands near the MIDI axis needed a fallback that brought the octave-sibling trap back. A review the same day reverted to pitch semantics for everything that is not a row the instrument lacks. The MIDI importer is the one caller that does NOT name a nominal: its snapped number was folded on the sounding axis and is a pitch. It had the mirror-image bug, looking that pitch up as a key name, so on a registered instrument every pitch that is also one of its key names landed on that key, a register away. Sky's Guitar (C3–C5, keys named C4–C6) took MIDI C4–C5 to its C3–C4 sound, colliding with the C3–C4 the file really had. It now finds the key by the pitch with the register taken off, and a pitch with no key stays itself. A file therefore imports at the pitch it says, and our own export re-imports unchanged on every registered instrument. A piano-range file dropped on Guitar now has its top octave out of range (dropped by default, as ADR-0012 decides for anything the chosen instrument cannot voice) instead of folded onto the keys an octave down; the offset suggestion is what fits it.

The composer also stops composing swaps at all within one audition. A run of instrument picks in the layer panel (one panel visit, one layer, nothing else edited in between) undoes the previous pick and swaps from the original (`instrumentPickSession.ts`). The run is one Undo Step, picking the original back leaves none (the withdrawn pick is not left on the redo stack either), and a long audition cannot accumulate hops. That holds even for the flavored instruments the register rule cannot make reversible.
