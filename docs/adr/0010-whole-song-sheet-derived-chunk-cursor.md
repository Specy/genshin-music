# The sheet shows the whole song, and the chunk cursor is derived

The player's visual sheet was built per run from the Section's slice alone: `playSong` and `practiceSong` chunked `notes.slice(start, end)` and handed the result to `playerControlsStore.setPages`, so frame 0 WAS the Section start and the last frame WAS its end. That equality was load-bearing — practice's queue and its pages were literally the same chunk objects ("they ARE the queue"), and both modes advanced `currentChunkIndex` incrementally on the assumption that chunk 0 = the run's first note. Approaching mode never built pages at all. The consequence surfaced the moment the sheet was asked to become an input rather than a display: a frame can only offer "Section starts here" for frames that exist, and a range-built sheet contains no frames outside the current Section — the loop could be narrowed from the sheet but never widened or moved, and a fullscreen "scroll to the part you want" view would show only the part already chosen.

We decided (2026-08-23): **pages are always built from the whole song (per-mode filtered), the Section renders ON the sheet as brackets and dimming, and the chunk cursor is derived from the absolute note position instead of incremented.** Every player-side chunk records the absolute note indices it spans, taken from the note's position in `song.notes` BEFORE any mode filter drops unplayables. `playerControlsStore` derives `currentChunkIndex`/`currentPageIndex` from `current` (already absolute — every run resets it to `start`) against those spans; nothing assumes chunk 0 is the run's start anymore. The Section (start inclusive, end exclusive, note-granular) stays the bound of what actually runs: play's plan slice, practice's queue and approaching's circle list are Section-bounded exactly as before — only the sheet stops being the queue.

Key choices within that:

- **One chunking per run per mode, spans annotated at the source.** The whole (mode-filtered) note list is chunked once; practice's queue is the chunks of that same list whose span intersects the Section, seam chunks trimmed by absolute index. Chunking the slice separately — the old way — produces boundaries that can disagree with the whole-song chunking near the seam (the merge window re-anchors at each chunk seed), and two chunk lists that drift make "which frame is current" unanswerable. The absolute index rides on the player's cloned notes as a runtime-only field, the same pattern as `displayButton`/`keyboardButton`: never serialized, filled at run setup, meaningless outside it.
- **The cursor is a pure function of `current`.** Play mode's note counting, practice's per-click advance and approaching's consumed circles all just move `current`; the chunk and page under the highlight follow by span lookup. This replaces `incrementChunkPositionAndSetCurrent`'s chunk-relative stepping, which could only ever be right while chunk 0 = run start. Practice jumps `current` to the next queue chunk's first absolute index on chunk completion, so unplayable notes inside a completed span cannot strand the highlight behind.
- **Approaching builds pages too.** Its circles were already made from the same playable, deduped notes practice chunks; the sheet is those chunks' whole-song version, and each resolved circle advances `current` past its note's absolute index. The mode was slider-only before not by design but because nobody wired it.
- **Out-of-Section frames are dimmed, never removed and never inert.** The whole point of showing them is that they are targets: "Section starts here", "Section ends here" and "Go to here" work on every frame. The chosen bound always wins — a bound that would cross its partner pushes the partner to its extreme (end → song length, start → 0) rather than being clamped away like the slider's thumbs, because a refused click on a distant frame reads as breakage, while two clicks (start here, end here) must be enough to move the Section anywhere.
- **Setting a bound never restarts the run; seeking always does.** Bounds share the slider's exact semantics — store write plus the lit restart hint — so the slider and the frames cannot disagree about what is pending. "Go to here" restarts at the frame's first note with the Section untouched; a target at or past the Section end runs to the song's end for that one run, so a seek is never a dead range and never a silent Section edit.

Considered and rejected: **keeping range-built pages** — smallest change, but brackets would pin to the first/last frame by construction and the sheet could only narrow, which fails the feature's premise. **A hybrid (inline range, fullscreen whole-song)** — two chunkings of the same song that disagree at the seam, frames that don't correspond 1:1 between the two views, and the inline card still can't widen. **Deriving practice's cursor by advancing one page-chunk per completed queue chunk** — holds only while queue and page chunk boundaries stay aligned, which the seam can break; deriving from absolute indices is immune to boundary drift.

Consequences: `Chunk` (the player-side one in `RecordedSong.ts`) carries its absolute note span; `playerControlsStore.incrementChunkPositionAndSetCurrent` and its chunk-relative stepping go away in favor of the derived lookup, and `setPages` takes span-annotated chunks. The sheet becomes interactive everywhere it renders — play included — through one shared card: frame popover ("Section starts here" / "Section ends here" / "Go to here"), accent brackets on the frames containing the bounds (always visible, full range included), dimmed out-of-Section frames, and a fullscreen mode that grows the card vertically at identical width, frame size and column count, centered once on the current chunk at open. The approaching score table moves beside the card. "Section" enters the glossary (CONTEXT.md) as the canonical term — the bounds constrain every run, with or without the Loop toggle — and the UI says Section, not Loop.
