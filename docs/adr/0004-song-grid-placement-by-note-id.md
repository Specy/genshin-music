# The composer canvas places every note by its Note Id on a game-defined grid, never by instrument button

The canvas positioned notes via `displayButtonForId` — the note's **own instrument's** button index fed into `composerPositions`. Button index equals canonical grid slot only for full-size (21-note) instruments, so the first melodic sub-grid instrument (`NightwindHorn`, 14 notes) exposed the flaw: its packed buttons 0–13 landed an octave band too high, the same Note Id rendered at two different rows depending on the track's instrument, and a track's stranded ids (canonical fallback rows, dimmed 0.45) collided with its misplaced healthy notes on the same rows — a stranded marker could even be masked entirely (`computeStrandedRows` clears rows with any healthy contributor). We decided the canvas places EVERY note, on every track, at the canonical Song-Grid row of its **Note Id** — one placement rule, no instrument involved — with the canonical ordered id list written **inline in `game.json`** next to `composerPositions` instead of the previous implicit source, "whatever `instruments.list[0]` happens to be". Registry evaluation validates that list as **one entry per Song Grid row** (`canonicalNoteIds.length === notes.perColumn`), duplicate-free, with every instrument's Note Ids drawn from it, and requires `composerPositions` only to be **at least** that long — not equal: sky's `composerPositions` carries six trailing rows (15-20 of a 15-row grid) left over from the legacy config that no instrument can index and that the frozen config-surface fixture pins, so only its first `perColumn` entries are ever read (the reason is documented at the check in `registry.ts`). Stranded notes keep exactly their current rendering (canonical row + dimming); only their collision with misplaced healthy notes disappears.

## Considered Options

- **Keep deriving the canonical list from the default instrument** — rejected: the Song Grid becomes an accident of menu roster order; reordering `instruments.list` (a cosmetic edit) would silently redefine or break the canvas.
- **Reference a `presets.json` Note Preset by name (e.g. `"standard-21"`)** — deferred, not rejected: avoids duplicating the id list, but we chose the inline list for now for directness; revisit if the duplication ever bites.
- **Per-Shape opt-out keeping drums packed top-left** — rejected: preserves the legacy drum visual at the cost of a second placement rule and a new config concept.
- **Id-based placement for the selected track only** — rejected: keeps two coordinate systems on one canvas.

## Consequences

- **Drum tracks change appearance vs the legacy app**: DunDun/DjemDjem ids (60–72) move from the packed top-left slots to their true pitch rows. The "visually identical to the pre-id format" guarantee is knowingly dropped for sub-grid instruments; the old visual was itself an artifact of the pre-id button-index format.
- The composer **keyboard** legitimately keeps own-button coordinates (its rows ARE the instrument's Buttons); the shared `computeRowLayerStatuses` helper must split into the two coordinate spaces instead of serving both with one answer.
- Anything that **edits by row moves with the canvas**, not with the keyboard: the move-notes-up/down tool (`ComposedSong.moveNotesBy`) steps through Song-Grid rows and takes the landing row's canonical id, because the rows the user is aiming at are the ones the canvas drew. Left on own buttons it silently disagreed with the surface it acts on — a sub-grid track's note would jump an octave band, or be deleted as though it were already on the top row with seven empty rows visible above it.
- The **sheet visualizer is deliberately untouched** for now: it still places by own button and letters frames with the default instrument's Label Set (wrong for horn and drums today). Its alignment with the Song Grid — or its re-definition as a per-instrument finger guide — is an open, separate decision.
- Canvas fixtures and the renderer tests that used `displayButtonForId` as the placement oracle regenerate/rewrite with the fix.
